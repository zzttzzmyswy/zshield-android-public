# 设备事务与只读观测接口方案（MYS-2840 后续卡提案）

本文是**未通过实现评审的提案**，不是实现或设备操作许可。本轮只做离线判据与安全边界；
`run` 在完整协议实现并验收前保持拒绝。
目的：把「正式版 Release APK 上无法取得输入证据」与「准备/采样/恢复不是一个事务」这两件事，
拆成能分别验收的最小改动，避免为了取证据去改生产、装调试包或读用户内容。

## 1. 现状：三个具体缺口

| # | 缺口 | 后果 | 现有入口 |
|---|---|---|---|
| 1 | 采样器未收到本进程解析的 serial/package | 准备与采样可能不是同一台设备 | `run_campaign` → `pss_idle.sh`（当前只吃 label/```--out```） |
| 2 | 准备阶段释放 canonical 锁，采样器再取锁 | 中间空窗可被其他任务占用 | `device-lock.sh`、`pss_idle.sh` 各自 `take` |
| 3 | 无恢复事务 | 中途失败可能留下改过的列表选择/用户规则 | 无 |

离线判据已就位（`inputs_proven` / `order_proven` 两层），所以缺口 1 的证据字段现在会被
`recompute` 直接判为缺失——协议补齐之前，设备数据无法冒充正式证据。

## 2. 只读观测接口（最小面）

目标：在不 root、不装调试包、不读用户内容的前提下，让正式 Release APK 能导出**够用于等价比较**的输入身份。

### 2.1 复用已有能力

仓库有列表导入与规则身份观测，但没有完整配置/列表正文导出，不能声称已有无损备份接口：

- `FilterRepository.importFile` 仅导入一个列表；`CertManager.exportToDownloads` 导出的是证书，
  两者都不能备份所有启用列表、正文与用户规则。
- `rules identity:` 行：候选版已输出 `dns/engine/extras` 的 `sha256:hex:bytes`，这是**内容身份**，
  直接对应 `loaded_artifacts_sha256`。
- 规则集选择与计数核对（`select_rule_set` 读 UI dump 的开关行）。
- 列表正文只在 App 私有目录，release 不可调试 → 这是当前「设备列表正文哈希」拿不到的根因。

### 2.2 需要新增的最小导出

一次显式触发（用户在设置页点「导出诊断信息」，或 `adb shell am broadcast` 一个**仅导出**的
受保护 receiver），写出一个 JSON 到 App 可写的外部目录：

```json
{
  "schema": 1,
  "build": {"version_name": "0.1.3", "version_code": 13, "apk_sha256": "…"},
  "rule_sets": {
    "fixed-five": {
      "lists": [{"id": "adguard-base", "enabled": true, "sha256": "…", "bytes": 6458941}],
      "user_rules_sha256": "…",
      "allowlist_sha256": "…",
      "loaded_artifacts_sha256": {"dns": "sha256:…:N", "engine": "sha256:…:N", "extras": "sha256:…:N"}
    }
  },
  "captured_at": "2026-11-13T00:00:00Z"
}
```

上述字段仅为待设计草案，不能直接宣称设备输入可比。导出者必须读取**编译消费的同一份字节**，
并绑定本次产物及实际加载代次；事后重新读取列表可能遇到下载/重编译，不能证明此前加载来源。
只导当前活动规则集，不凭名称生成其他规则集记录。未确认 generation 一致就返回 unknown。

原版 v0.1.2 没有此接口。给重编译的 v0.1.2 加观测代码不再是原 Release，不能借用原 APK 哈希；
如采用该对照，必须单列构建来源、差异和开销验证，先由负责人确定测量口径。

### 2.3 敏感边界

- **不含**：规则正文、用户自定义规则正文、allowlist 正文、浏览/连接记录、设备标识。
  只导哈希与计数，仍按诊断数据管理：低熵用户内容的哈希可能被猜测，不宣称完全不含敏感信息。
- **不含私钥**：CA 私钥、App 私钥、release keystore 一律不进导出；`assemble_evidence.py` 对
  这些文件名已经硬拒绝。
- 哈希用 SHA-256 对**设备上实际加载的字节**计算，而不是宿主 catalog；宿主哈希不能替代。
- 导出目录用 App 自己的 external files dir，不需要 root，不需要 `run-as`。

### 2.4 如何避免误判正式包

App 自身 APK 哈希与 `pm path` 的独立读数相等只证明相互一致。两者还必须与负责人固定的
Release 产物 SHA/构建来源匹配；否则侧载或调试包也可通过自证。receiver 若实现，必须确定
具体权限、调用者校验、写入位置与拒绝行为并测试；此提案不授权新增开放导出组件。

## 3. 事务协议（准备 → 采样 → 恢复）

复用现有 `device-lock.sh` 的 owner/token/guard/续期，不新建锁协议；设计单一事务持有者：

1. **单一入口取锁**：`run` 只调用一次 `device-lock.sh take`，拿到租约（owner + token + 过期时间），
   **不再在准备结束后释放**。
2. **传递而非重取**：租约通过环境变量/参数传给 `pss_idle.sh`；采样器校验 token 而不是自己
   `take`。这样缺口 1、2 同时消失：同一 serial/package/租约贯穿准备与采样。
3. **恢复登记**：修改前验证备份可恢复。哈希只是核验依据，不能代替原 APK、列表正文与用户
   配置备份；配置必须有可执行的恢复入口。清日志无法还原，因此使用日志边界，不清共享日志。
   force-stop 后可恢复 VPN 开关等状态，不能承诺恢复原进程。APK 降级若需卸载/清数据则拒绝。
4. **恢复执行**：正常结束与任何失败路径都走同一个 `finally`：按清单逆序还原，逐项核验，
   结果写 `recovery.json`；任一项未核验成功 → `run` 返回非零且 `campaign.json` 记 void。
5. **所有权丢失**：续期失败后停止设备写入，记录未恢复项；不得在新 owner 持锁时执行 finally
   恢复，也不得让下一持有者自动执行旧任务恢复单。保留证据，等待明确的恢复安排。

### 3.1 验收这些改动的离线可测部分

事务协议大部分能在**假设备**上验证，不需要真机：`tests/test_acceptance_entry.py` 的
`StubDevice` 已经提供可计数的 adb 替身。需要补的用例：

- 采样器收到的是准备的 serial/package/租约 token（参数断言，零真机）；
- 准备与采样之间没有 `release`（调用序列断言）；
- 任一步注入失败后，`restore.json` 每一项都被执行且核验（假设备状态回读）；
- 恢复失败的 campaign `recompute` 判为不可用（已有分层模型直接覆盖）。

协议测试先在假设备完成，包括其他 owner、续期失败、写入失败及恢复失败；通过后才安排
独占设备的有界冒烟。连接/会话改动另按项目要求做并发验证，不把主机测试当真机验收。

## 4. 明确不做

- 不加 root、不改生产过滤、不为取证据改 `version.properties` 之外的产物。
- 不把宿主数字当设备数据；`docs/I2_MEMORY_PROFILE.md` 已把宿主实验限定为组件探针。
- 不在协议验收前放开 `run`；本轮的拒绝是永久行为直到本方案被接受。
- 不用「两版都超标」证明「无回归」，不放宽 84.6 MiB。

## 5. 建议的下一张卡切分

| 卡 | 范围 | 可离线验收 |
|---|---|---|
| A | 只读观测导出（§2） | 是：导出 schema、哈希来源、无敏感字段、apk 自证 |
| B | 事务协议（§3 的 1/2/5） | 是：假设备上的取锁顺序与租约传递 |
| C | 恢复清单与恢复事务（§3 的 3/4） | 是：故障注入后的还原核验 |
| D | 真机交替矩阵 | 否：需独占 Pixel，协议 A–C 合入后单独排期 |
